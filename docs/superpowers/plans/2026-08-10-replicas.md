# Replicas Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implement DeRec replicas — a second device of the same Owner that mirrors the vault — for both provisioned and browser-based replicas, covering pairing, fingerprint confirmation, secret mirroring, vault adoption, and takeover.

**Architecture:** A replica destination runs in a **separate browser context** with its **own `replicaId`**, and after its first sync it **wipes its local vault and adopts the source's `secretId`** via the library's existing `restore()` path. The previous replica implementation is removed wholesale, not adapted.

**Tech Stack:** React 19 + TypeScript + Vite (frontend), Rust + Axum + actix actors (backend), `@derec-alliance/web` WASM bindings, Vitest (new).

**Spec:** `docs/superpowers/specs/2026-08-10-replicas-design.md`

## Global Constraints

- **C1 — one user per browser context.** No device-switcher, no two live protocol instances in one tab. A replica is set up by opening incognito / another profile / another browser.
- **C2 — one vault per user.** A device that syncs as a replica erases its own vault and adopts the source's. No coexistence.
- **Identity rule:** a replica destination is *source's `secretId`, own `replicaId`, own browser context*.
- **`replicaId` is device-scoped, not vault-scoped.** It MUST be stored outside any `derec:<ns>:` namespace so `clearNamespace()` during adoption does not rotate it.
- **Both sides of a replica pair need a `replicaId`.** The Owner is the `ReplicaSource`. Omitting it yields `ReplicaIdNotConfigured`.
- **Fingerprint confirmation is bilateral and human-driven** on both provisioned and browser replicas.
- **Adoption is gated on explicit user confirmation** before any wipe.
- No `any` in TypeScript. No `unwrap()` in Rust production paths. MUI used idiomatically. Handlers stay thin.
- **Commit policy: implementers NEVER commit and NEVER stage.** No `git commit`, no `git add`, and absolutely no `git add -A`. All work accumulates in the working tree; the human partner reviews and commits once, at the end of the plan. Every task's final step is a report of touched files, not a commit.

```ts
/**
 * This device's stable replica identity.
 *
 * The DeRec protocol carries a per-device `u64` under the reserved
 * `derec.replica_id` key; any replica-mode flow on a protocol built without
 * one fails with `ReplicaIdNotConfigured`. Both sides of a replica pair need
 * one — the Owner is the `ReplicaSource`.
 *
 * The key sits outside every `derec:<ns>:` partition on purpose. Adoption
 * wipes a namespace to take on another device's vault; the device's own
 * identity must survive that, or it would silently become a different peer.
 */

const STORAGE_KEY = 'derec:replica-id'

function mint(): bigint {
  const buf = new BigUint64Array(1)
  crypto.getRandomValues(buf)
  return buf[0]
}

/** This device's replica id, minting and persisting one on first use. */
export function getOrCreateReplicaId(): bigint {
  const stored = localStorage.getItem(STORAGE_KEY)
  if (stored !== null) {
    try {
      return BigInt(stored)
    } catch {
      // Corrupt value — fall through and mint a fresh one.
    }
  }
  const id = mint()
  localStorage.setItem(STORAGE_KEY, id.toString())
  return id
}

/** Drops the stored identity. Only for explicit "reset this device" actions. */
export function resetReplicaId(): void {
  localStorage.removeItem(STORAGE_KEY)
}
```

```ts
import { SenderKind } from '@derec-alliance/web'

/**
 * App-level pairing roles.
 *
 * Pairing is unidirectional in both modes: Owner↔Helper for participants,
 * ReplicaSource↔ReplicaDestination for replicas. A channel's role is fixed
 * at handshake time and stored on the channel record.
 */
export type PairingRole = 'owner' | 'helper' | 'replica_source' | 'replica_destination'

/** `SenderKind` for an app-level pairing role. */
export function senderKindFor(role: PairingRole): SenderKind {
  switch (role) {
    case 'owner':
      return SenderKind.Owner
    case 'helper':
      return SenderKind.Helper
    case 'replica_source':
      return SenderKind.ReplicaSource
    case 'replica_destination':
      return SenderKind.ReplicaDestination
  }
}

/** The role that complements `role` — what the other side of a channel takes. */
export function complementRole(role: PairingRole): PairingRole {
  switch (role) {
    case 'owner':
      return 'helper'
    case 'helper':
      return 'owner'
    case 'replica_source':
      return 'replica_destination'
    case 'replica_destination':
      return 'replica_source'
  }
}

/** Whether `role` takes part in a replica-mode pairing. */
export function isReplicaRole(role: PairingRole): boolean {
  return role === 'replica_source' || role === 'replica_destination'
}
```

```rust
/// Decides the `secret_id` a newly spawned actor binds its protocol to.
///
/// A replica destination mirrors the owner's vault, and the share store keys
/// on `(secret_id, channel_id, version, replica_id)` — a destination under a

fn actor_secret_id(role: Role, owner_secret_id: Option<u64>) -> u64 {
    match (role, owner_secret_id) {
        (Role::Replica, Some(owner)) => owner,
        _ => rand::random::<u64>(),

}
```

- [ ] **Step 3: Write the implementation**

Create `apps/backend/src/routes/replicas.rs` with a resolver that accepts both actor kinds, and handlers for add / fingerprint / confirm-fingerprint / toggle-status. Handlers stay thin: validate session and replica exist, resolve the actor, delegate to the actor for `GetFingerprintMsg` / `VerifyFingerprintMsg`, map results to status codes (`404` unknown session/replica, `409` not yet paired, `400` fingerprint mismatch, `500` actor/mailbox failure), and return the existing structured-JSON error shape.

**A replica belongs to a specific owner, not to the session.** A session may legitimately hold several `Role::Owner` actors — `join()`'s normal path (the plain "Invite to Session" QR flow) mints a new independent owner with its own `secret_id` by design. `AddReplicaRequest` therefore carries an explicit `owner_actor_id: Uuid` naming which owner's vault this replica mirrors.

`add_replica` must:

### Task 18: Library-aligned `paired`, and an explicit sync action

Two decisions from the project owner, plus the ordering hazard that motivates them.

**Decision A — app `paired` follows the library's channel status.** Today `nextReplicaStatus` requires `localConfirmed && peerConfirmed`. **Decision B — the source must be able to trigger a sync explicitly.** A "Sync now" action on the source's replica row.

### Task 19: Tell the user what is happening — expiry warning and visible sync failure

The project owner reviewed the library and concluded its behaviour is correct as-is; the problem is that the app does not communicate it. Two requirements, both UX.

**Requirement 1 — a pending replica channel silently expires.** `cleanup_expired_channels` (`lib-derec` `protocol/mod.rs:1819-1849`) removes any channel still `Pending` when `now - channel.created_at > timeout`, where `timeout` is the protocol timeout the app itself configured via `withTimeout` (`session.config.protocolTimeoutSecs`, default 300s). The clock runs from **channel creation**, not last activity. Today the fingerprint UI gives no hint of this, so a user comparing codes at leisure can lose the channel with no explanation.

**`created_at` is NOT available to the frontend** — it appears in neither `apps/web/src/stores.ts` nor `lib-derec/library/target/pkg-web/index.d.ts`. The app must stamp its own timestamp when the replica pairing completes, in the existing local replica record (Task 17, keyed by channel id under `derec:replica-state:<sessionId>`).
